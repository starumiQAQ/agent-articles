# Building Effective Agents（构建有效的 AI 智能体）

> **原文**: [Building effective agents](https://www.anthropic.com/engineering/building-effective-agents)
> **作者**: Erik S. & Barry Zhang (Anthropic)
> **发布时间**: 2024-12-19
> **翻译**: 中文翻译

---

我们与数十个团队合作，在不同行业中构建 LLM 智能体。一致地，最成功的实现使用的是**简单、可组合的模式**，而非复杂框架。

过去一年，我们与数十个跨行业构建大语言模型（LLM）智能体的团队合作过。一致地，最成功的实现并非使用复杂的框架或专门的库。相反，它们是用简单、可组合的模式构建的。

在这篇文章中，我们将分享与客户合作以及我们自己构建智能体过程中学到的经验，并为开发者提供构建有效智能体的实用建议。

---

## 什么是智能体？（What are agents?）

"智能体"可以有多种定义。一些客户将智能体定义为**完全自主的系统**——能够长时间独立运行，使用各种工具完成复杂任务。另一些人则用这个词来描述更受约束的实现，遵循预定义的工作流。

在 Anthropic，我们将所有这些变体归类为**智能体系统（agentic systems）**，但在架构层面上区分**工作流（workflows）**和**智能体（agents）**：

- **工作流**：LLM 和工具通过预定义的代码路径编排的系统。
- **智能体**：LLM 动态地指导自身过程和工具使用的系统，保持对如何完成任务的控制。

下文将详细探讨两种智能体系统。在附录 1（"实践中的智能体"）中，我们描述了客户发现此类系统特别有价值的两个领域。

---

## 何时（以及何时不）使用智能体

在构建 LLM 应用程序时，我们建议**找到最简单的可行方案，仅在需要时增加复杂度**。这意味着可能根本不需要构建智能体系统。智能体系统通常以延迟和成本换取更好的任务性能，你需要权衡这种取舍是否合理。

当确实需要更复杂的方案时：

- **工作流**适合定义明确的任务，提供可预测性和一致性
- **智能体**则是需要灵活性和模型驱动决策的大规模场景的更优选择

然而，对于许多应用场景，优化单次 LLM 调用（配合检索和上下文示例）通常就已足够。

---

## 何时以及如何使用框架

有许多框架可以简化智能体系统的实现，包括：

- **Claude Agent SDK**
- **AWS 的 Strands Agents SDK**
- **Rivet** — 拖放式 GUI LLM 工作流构建器
- **Vellum** — 另一个用于构建和测试复杂工作流的 GUI 工具

这些框架通过简化底层任务（调用 LLM、定义和解析工具、串联调用）让你快速上手。然而，它们往往增加抽象层，掩盖底层提示词和响应，使调试更加困难。它们也可能诱使你增加复杂性，而简单的方案本已足够。

我们建议开发者**直接从 LLM API 开始**：许多模式只需几行代码即可实现。如果确实使用框架，请确保理解底层代码。对底层机制的错误假设是客户出错的常见来源。

## 构建模块、工作流和智能体

在本节中，我们将探索在生产环境中看到的智能体系统的常见模式。从基础构建模块——**增强型 LLM**——开始，逐步增加复杂度，从简单的组合式工作流到自主智能体。

### 构建模块：增强型 LLM（The Augmented LLM）

智能体系统的基本构建模块是经过**检索、工具和记忆**等增强的 LLM。我们当前的模型可以主动使用这些能力——生成自己的搜索查询、选择合适的工具、决定保留什么信息。

```
                   增强型 LLM
                        │
        ┌───────────────┼───────────────┐
        │               │               │
      检索             工具             记忆
```

我们建议关注实现中的两个关键方面：**根据具体用例定制这些能力**，并**确保它们为 LLM 提供简单且文档清晰的接口**。虽然有很多方式实现这些增强，一种方法是使用我们最近发布的 **Model Context Protocol (MCP)**，它允许开发者通过简单的客户端实现与不断增长的第三方工具生态集成。

在本文后续部分，我们假设每次 LLM 调用都具备这些增强能力。

---

### 工作流：提示链（Prompt Chaining）

提示链将任务分解为一系列步骤，每次 LLM 调用都处理前一次调用的输出。你可以在任何中间步骤添加**程序化检查**（"门控"），确保过程仍在正轨上。

```
输入 → LLM 调用 → 门控(检查) → LLM 调用 → 门控(检查) → ... → 输出
                          ↓ (失败)
                       提前退出
```

**何时使用：** 适用于任务可以被轻松、干净地分解为固定子任务的情况。主要目标是以延迟换取更高的准确性，使每次 LLM 调用都成为更简单的任务。

**示例：**
- 生成营销文案，然后翻译成另一种语言
- 编写文档大纲，检查大纲是否符合某些标准，然后基于大纲撰写文档

---

### 工作流：路由（Routing）

路由将输入分类并导向专门的后续任务。这种工作流允许关注点分离，构建更专业的提示词。没有路由，优化某一类输入会损害其他输入的性能。

```
        输入
          │
      分类器/LLM
       ┌──┴──┐
       │     │
    类别A   类别B
       │     │
    专业处理  专业处理
```

**何时使用：** 适用于存在不同类别需要分别处理、且分类可以准确完成的复杂任务（分类可由 LLM 或更传统的分类模型/算法完成）。

**示例：**
- 将不同类型的客服查询（普通问题、退款请求、技术支持）导向不同的下游流程、提示词和工具
- 将简单/常见问题路由到更小、更经济的模型（如 Claude Haiku），将困难/罕见问题路由到能力更强的模型（如 Claude Sonnet），以优化性能

---

### 工作流：并行化（Parallelization）

LLM 可以同时处理一项任务，然后将输出程序化地聚合。这种工作流有两种关键变体：

- **分段（Sectioning）**：将任务分解为独立的子任务并行运行
- **投票（Voting）**：多次运行相同任务以获得多样化的输出

```
        输入
       ┌──┴──┐
    LLM-A  LLM-B    ← 并行运行
       └──┬──┘
       聚合结果
```

**何时使用：** 当分解的子任务可以并行化以提升速度，或需要多种视角或多次尝试以获得更高可信度的结果时。

**分段示例：**
- 实现护栏：一个模型实例处理用户查询，另一个筛选不当内容或请求——这通常比让同一个 LLM 同时处理两者表现更好
- 自动化评估：每个 LLM 调用评估模型在给定提示词上不同方面的表现

**投票示例：**
- 审查代码漏洞：多个不同的提示词审查代码，如果发现问题则标记
- 评估内容是否不当：多个提示词评估不同方面，或要求不同的投票阈值以平衡误报和漏报

---

### 工作流：编排器-工作者（Orchestrator-Workers）

在编排器-工作者工作流中，一个中央 LLM 动态地分解任务，将其委派给工作者 LLM，并综合它们的结果。

```
             编排器 LLM
          ┌─────┼─────┐
       工作者1 工作者2 工作者3
          └─────┼─────┘
             综合结果
```

**何时使用：** 适用于无法预知所需子任务的复杂任务（例如编码中需要修改的文件数量以及每个文件中的变更类型因任务而异）。

**示例：**
- 需要对多个文件进行一系列变更的编码产品
- 涉及从多个来源收集和分析信息的搜索任务（可能需要在多个来源上并行运行搜索）

---

### 工作流：评估器-优化器（Evaluator-Optimizer）

在此工作流中，一个 LLM 调用生成响应，另一个 LLM 调用评估并提供反馈，形成循环。

```
生成器 LLM → 输出 → 评估器 LLM
    ↑                    │
    └──── 反馈 ──────────┘
```

**何时使用：** 当有明确的评估标准，且迭代改进能带来可量化价值时效果最佳。两个关键要素：一是"评估者"需要提供充分好的反馈让 LLM 改进；二是迭代价值要足够高，值得付出额外延迟。

**示例：**
- 文学翻译：译者 LLM 可能无法在一开始就捕捉到细微差别，但评估者 LLM 可以提供有用的批评
- 复杂搜索任务：需要多轮搜索和分析才能收集全面信息，评估者决定是否需要进一步搜索

## 智能体（Agents）

当工作流的灵活性不足时，智能体是 LLM 动态地指导自身过程和工具使用的系统。与工作流不同，智能体拥有广泛的工具集，且每一步的输入输出都可以访问这些工具。它们本质上是一个在循环中使用工具、根据自身判断决策的 LLM。

```
循环:
  LLM 思考 → 选择工具/行动 → 观察结果 → LLM 再思考 → ...
```

**何时使用：** 在需要灵活性和模型驱动决策的大规模应用中最有价值。智能体最适合那些**很难或无法预知所需步骤数量**的问题，且你不能硬编码固定路径的场景。

**示例：**
- 解决 SWE-bench 任务：代理编辑多个文件，需要查看文件内容、分析错误、进行修改等
- 大规模客户支持：智能体查看文档、执行退款、创建工单等，每一步的行动都取决于对话情境

### 智能体设计模式

在生产环境中，我们观察到成功的智能体实现通常具备以下特征：

1. **简单的工具集**：不要给智能体太多工具，专注于核心能力
2. **清晰的决策边界**：智能体知道何时可以自主决策，何时需要人类介入
3. **透明的思考过程**：让智能体的规划步骤可见，便于调试和信任
4. **避免复杂循环**：简单的循环结构通常比复杂的状态机更可靠

## 工具设计（Tool Design）

无论构建哪种智能体系统，工具都将是重要组成部分。工具使 Claude 能够与外部服务和 API 交互。**工具定义和规范应得到与整体提示词同样程度的重视。**

**关键原则：**

- **给模型足够的"思考"空间**，避免让它把自己逼入角落
- **保持格式接近模型在互联网文本中自然见到的形式**
- **避免格式化开销**：例如维护数千行代码的准确计数或转义代码中的引号

### Agent-Computer Interface（ACI）理念

我们可以用 HCI（人机交互）领域的经验——投入同样的精力来设计良好的智能体-计算机接口（ACI）：

- **站在模型的角度**：这个工具的使用方式是否显而易见？好的工具定义通常包含示例用法、边界情况、输入格式要求，以及与其他工具的清晰边界
- **测试模型如何使用你的工具**：运行大量示例输入，观察模型犯什么错误，然后迭代
- **防错设计（Poka-yoke）**：设计参数使其更难以犯错。例如，我们在构建 SWE-bench 智能体时发现模型在使用相对路径时会出错，于是改为始终要求绝对路径——模型此后完美地使用了这一方法

---

## 关键原则

1. **保持简单**：从最简单的方案开始，只在必要时增加复杂度
2. **追求透明**：明确展示智能体的规划步骤
3. **精心设计 ACI**：通过完善的工具文档和测试来打磨智能体与工具的交互

## 附录 1：实践中的智能体（Agents in Practice）

### A. 客户支持

客户支持将熟悉的聊天机器人界面与工具集成能力相结合。这是一个适合开放性智能体的场景，因为：

- 支持对话自然遵循对话流程，同时需要访问外部信息和操作
- 可以集成工具来拉取客户数据、订单历史、知识库文章
- 退款、更新工单等操作可以程序化处理
- 成功可以通过用户定义的解决方案清晰衡量

多家公司已经通过按成功解决收费的用量定价模型，展示了这种方法的可行性。

### B. 编程智能体

软件开发领域展现了 LLM 功能的显著潜力，从代码补全发展到自主问题解决。智能体特别有效是因为：

- 代码解决方案可以通过自动化测试验证
- 智能体可以使用测试结果作为反馈来迭代方案
- 问题空间定义明确且结构化
- 输出质量可以客观衡量

在 Anthropic 自己的实现中，智能体已能仅凭 PR 描述就解决 SWE-bench Verified 基准中的真实 GitHub 问题。但自动化测试验证功能的同时，**人工审查对确保解决方案符合整体系统要求仍然至关重要**。

## 附录 2：提示工程你的工具（Prompt Engineering Your Tools）

无论构建哪种智能体系统，工具都将是重要组成部分。工具使 Claude 能够通过 API 中指定的结构定义与外部服务和 API 交互。

有时定义相同动作有多种方式。例如，你可以通过写 diff 或重写整个文件来指定文件编辑。对于结构化输出，你可以在 markdown 或 JSON 中返回代码。在软件工程中，这些差异是表面性的，可以无损转换。

然而，某些格式对 LLM 来说比其他的更难编写：

- 写 diff 需要知道新代码写入前块头中有多少行在变化
- 在 JSON 中写代码（相对于 markdown）需要额外转义换行符和引号

**关于工具格式的建议：**

1. 给模型足够的 token 来"思考"，避免把自己逼入角落
2. 保持格式接近模型在互联网文本中自然见到的形式
3. 避免格式化"开销"，如维护数千行代码的准确计数或字符串转义
